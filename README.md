# gatekeeper

JWT/RBAC gateway на Rust: единый сервис, который проверяет JWT, применяет RBAC-правила и проксирует HTTP-запросы на upstream.

**Учебный проект** для изучения Rust, асинхронного программирования и построения HTTP-сервисов.

> **Статус:** функционально завершён, учебный проект. Не проходил полноценный аудит безопасности и комплексное нагрузочное тестирование. Использование в production — на свой риск.

## Возможности

- **JWT-аутентификация:** алгоритм проверки определяется конфигурацией и ключом из JWKS, а не заголовком токена; проверяются подпись, `exp`, `iss` и `aud`.
- **JWKS:** ключи обновляются по расписанию. Неизвестный `kid` приводит к `401` без обращения к провайдеру во время обработки запроса.
- **Асимметричные алгоритмы:** симметричные алгоритмы `HS*` и ключи типа `oct` запрещены.
- **RBAC:** deny by default; правила нескольких ролей объединяются, доступ разрешается при совпадении хотя бы одного allow-правила.
- **Кэш правил:** правила загружаются по HTTP, хранятся в памяти с использованием `ArcSwap` и обновляются по расписанию. При ошибке обновления сохраняется последний рабочий снимок.
- **Шаблоны путей:** литералы, `{param}`, `**` только в конце шаблона.
- **Публичные эндпоинты:** настраиваются в том же наборе правил и обходят JWT-аутентификацию.
- **Валидация пути:** запрещаются `.` и `..`, пустые сегменты, `%2e`, `%2f`, `%5c`, обратный слеш, `;` и управляющие символы.
- **Проксирование:** потоковая передача тела запроса, ограничение размера запроса и удаление hop-by-hop заголовков.
- **Request ID и трассировка:** генерация `x-request-id`; логи запросов не содержат query-параметры и токены.
- **Health checks:** отдельные эндпоинты для проверки жизнеспособности и готовности сервиса.

## Порядок обработки запроса

1. Валидация пути — `400`.
2. Получение снимка RBAC-правил — `503`, если правила ещё не загружены. (Приложение не запустится, если правила не загружены)
3. Проверка публичного пути — без чтения токена.
4. Проверка Bearer-токена, поиск ключа по `kid`, проверка подписи и claims — `401` при ошибке.
5. Проверка ролей по RBAC-правилам — `403` при отсутствии доступа.
6. Проксирование запроса на upstream.

`GET /health/live` и `GET /health/ready` находятся вне этой цепочки.

## Заголовки upstream

Для аутентифицированных запросов gateway добавляет:

- `x-user-id` — значение claim `sub`;
- `x-user-roles` — список ролей через запятую.

Дополнительно:

- входящие `x-user-id` и `x-user-roles` удаляются всегда, включая публичные пути;
- `Authorization`, `Host` и hop-by-hop заголовки не передаются upstream;
- клиентский `x-request-id` заменяется сгенерированным gateway идентификатором.

**Важно:** upstream должен доверять этим заголовкам только при получении запросов через gateway и не должен быть доступен в обход него.

## Конфигурация

| Переменная | Обязательна | Описание |
|---|---|---|
| `BIND_ADDR` | Нет (`0.0.0.0:8080`) | Адрес и порт HTTP-сервера |
| `UPSTREAM_URL` | Да | URL целевого сервиса |
| `RULES_URL` | Да | URL источника RBAC-правил |
| `RULES_REFRESH_SECS` | Нет (`60`) | Период обновления правил, больше 0 |
| `JWKS_URL` | Да | URL набора публичных ключей |
| `JWKS_REFRESH_SECS` | Нет (`300`) | Период обновления JWKS, больше 0 |
| `JWT_ISSUER` | Да | Ожидаемое значение `iss` |
| `JWT_AUDIENCE` | Да | Ожидаемое значение `aud` |
| `JWT_ALGORITHMS` | Нет (`RS256`) | Разрешённые алгоритмы через запятую; `HS*` запрещены |
| `MAX_BODY_MB` | Нет (`10`) | Максимальный размер тела запроса в МБ, больше 0 |
| `RUST_LOG` | Нет (`info`) | Уровень логирования |

## Формат RBAC-правил

```json
{
  "public": [
    { "method": "POST", "path": "/auth/login" }
  ],
  "rules": {
    "admin": [
      { "method": "*", "path": "/api/**" }
    ],
    "user": [
      { "method": "GET", "path": "/api/users/{id}" }
    ]
  }
}
```

- `method` — HTTP-метод или `*`.
- `path` должен начинаться с `/`.
- `{id}` совпадает с одним непустым сегментом пути.
- `**` допустим только в конце и совпадает с любым хвостом, включая пустой.
- Неизвестные поля и некорректные правила приводят к отклонению всего набора.
- Роль с пустым списком правил допустима.
- Набор без единого правила для ролей считается ошибкой источника.
- `*` и `/**` в `public` разрешены намеренно: ответственность за содержимое публичных правил лежит на владельце конфигурации.

## Нагрузочное тестирование

Для предварительной оценки производительности использовался локальный стенд Docker Compose с gateway, mock upstream, Keycloak и k6.

Сценарий k6 отправляет запросы с разными исходами проверки доступа: разрешённые запросы, `403`, `401` и публичные запросы. Токены получают в `setup()`, поэтому Keycloak не участвует в обработке каждого запроса.

### Результаты

| Целевая скорость запуска итераций | Средняя фактическая скорость за весь прогон | HTTP-запросы | p95 разрешённых admin-запросов | RAM gateway | Пропущенные итерации |
|---:|---:|---:|---:|---:|---:|
| 200 итераций/с | ~144 итерации/с | 7 201 | 1,39 мс | ~5МБ* | 0 |
| 5 000 итераций/с | ~4 219 итераций/с | 380 001 | 1,23 мс | ~10 МБ* | 0 |
| 10 000 итераций/с | ~8 439 итераций/с | 760 001 | 4,43 мс | ~20 МБ* | 0 |
| 20 000 итераций/с | ~11 373 итерации/с | 1 024 211 | 309,08 мс | ~200 МБ* | 495 790 |

Дополнительные результаты:

- При целевой скорости 5 000 итераций/с p99 разрешённых admin-запросов составил около **2,38 мс**.
- При 10 000 итераций/с p99 разрешённых admin-запросов составил около **7,73 мс**.
- При 20 000 итераций/с p95 всех HTTP-запросов составил около **299 мс**.
- Наибольшее потребление памяти gateway в простое составляло около **2 МБ** по наблюдениям.

\* Потребление памяти — приблизительные значения, наблюдавшиеся во время локальных прогонов; это не результат отдельного профилирования памяти. Подобный рост вызван упором в процессор и заполнения буффера

### Условия и интерпретация

- Тесты проводились на локальном Docker Compose-стенде. Gateway, k6 и остальные компоненты делили ресурсы одной машины.
- Сценарий использовал ramping arrival rate: разгон, удержание целевой скорости и снижение нагрузки. Поэтому средняя скорость за весь прогон закономерно ниже целевой скорости на этапе удержания.
- При 5 000 и 10 000 итераций/с k6 не зарегистрировал пропущенных итераций, а проверки сценария прошли успешно.
- При 20 000 итераций/с k6 достиг лимита в **2 000 VU** и начал пропускать итерации. Одновременно выросли задержки и потребление CPU.
- Во время максимальной нагрузки gateway потреблял около **600% CPU**, а k6 — около **500%**. Остальные сервисы и операционная система также использовали ресурсы машины.

**Вывод:** в данном окружении нагрузка до 10 000 итераций/с проходила без пропусков со стороны k6 и с небольшими задержками. При целевых 20 000 итераций/с стенд не смог поддерживать заданную скорость.

Эти результаты характеризуют конкретный локальный стенд, а не максимальную производительность самого gateway. Для определения предела прокси необходимо отдельно проверить влияние генератора нагрузки, mock upstream и конкуренции за CPU.

## Известные ограничения

- Новый `kid` после ротации ключей принимается только после следующего обновления JWKS.
- Один HTTP-клиент с общим таймаутом используется и для служебных вызовов, и для проксирования. Медленные или большие ответы upstream могут упираться в этот таймаут и приводить к `504`.
- Chunked-тело, превысившее лимит, приводит к `502`, а не `413`.
- Размер ответов источников RBAC-правил и JWKS не ограничен.
- Двойное кодирование пути, например `%252e`, отдельно не отслеживается.
- Паника в фоновом цикле обновления может остановить его без автоматического восстановления; `/health/ready` при этом может оставаться зелёным.
- Отзыв ключа или правила вступает в силу с задержкой до следующего обновления кэша.
- Редиректы upstream не выполняются автоматически, а возвращаются клиенту как есть.
- Проект не проходил полноценный аудит безопасности и комплексное нагрузочное тестирование.
